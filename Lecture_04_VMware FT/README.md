# 4 Fault-Tolerance

## 4.1 复制 Replication

这部分讲义主要探讨了**容错（Fault-Tolerance）**的核心概念，重点介绍了**复制（Replication）**技术的作用范围、局限性以及经济考量。

以下是该部分内容的详细总结：

**1. 复制的目标：高可用性**

- 容错的目的是为了提供**高可用性（High Availability）**。
- 即使硬件故障或网络出现问题，通过复制技术，服务依然能够持续对外提供功能。

**2. 复制能解决什么故障？（Fail-stop）**

- 复制主要处理的是 **Fail-stop 故障**。
- **定义**：指计算机遇到故障时直接停止运行（Stop），而不是计算出错误的结果。
- **例子**：电源被拔掉、网线被拔掉、风扇故障导致CPU过热关机等。
- **机制**：对于部分随机的硬件错误（如网络传输的比特翻转、磁盘坏道），可以通过校验和或纠错码检测出来，将其转化为 Fail-stop 错误，从而让复制机制接管。

**3. 复制不能解决什么故障？**

- **软件 Bug**：如果主节点软件有 Bug，副本节点运行完全相同的软件，会产生完全相同的错误结果，复制对此无能为力。
- **硬件设计缺陷**：同样的硬件漏洞会导致所有副本计算出同样的错误。
- **关联错误（Correlated Failures）**：
  - **制造缺陷**：如果所有副本使用的是同一批次有缺陷的硬件（如散热不足），可能会同时故障。
  - **环境灾难**：如地震、停电或火灾摧毁整个数据中心。要解决这类问题，必须将副本部署在物理上隔离的不同地点（如不同城市）。

**4. 复制的成本与经济考量**

- **成本高昂**：复制意味着资源消耗翻倍（如 GFS 需要3倍磁盘，VMware FT 需要2倍机器、CPU、内存）。
- **是否值得**：这是一个**经济问题**而非纯技术问题。
  - 对于关键服务（如银行），停机意味着巨大的经济损失和用户流失，因此昂贵的复制是值得的。
  - 对于非关键服务（如课程网站），停机后果很小，可能就不值得投入高昂的成本做热备份。

**总结来说**，这段讲义强调了复制是处理**独立硬件故障（Fail-stop）\**的有效手段，但它不是万能的（无法解决 Bug 或关联故障），且实施时需要权衡\**成本与服务价值**。



## 4.2 复制方法深度解析：状态转移与复制状态机

在构建容错系统时，复制（Replication）是核心手段。本节课重点讨论两种主要的复制策略：**状态转移 (State Transfer)** 和 **复制状态机 (Replicated State Machine)**，并深入探讨 VMware FT 为何选择后者及其独特性。

#### 1. 两种核心复制方法

##### A. 状态转移 (State Transfer)

- **核心思想**：Primary 节点定期将自身的**完整状态**（例如全部内存镜像、数据库快照）拷贝并发送给 Backup 节点。
- **工作机制**：
  1. Primary 运行一段时间。
  2. Primary 暂停或快照，将全部内存内容打包。
  3. 通过网络发送给 Backup。
  4. Backup 接收并覆盖自身状态。
  5. 当 Primary 故障时，Backup 从最近一次接收到的完整状态开始运行。
- **优化**：为了效率，通常只发送增量变更（上次同步后修改的内存页）。
- **优点**：
  - **实现简单粗暴**：不需要理解操作逻辑，只管搬运数据。
  - **多核友好**：状态快照不受并行计算不确定性的影响（VMware 后来针对多核 CPU 推出的新系统就转向了类似思路）。
- **缺点**：
  - **带宽消耗巨大**：状态（State）通常很大（GB/TB 级别），网络传输开销极高。

##### B. 复制状态机 (Replicated State Machine) —— **本课程重点**

- **核心思想**：利用计算机软件的确定性（Deterministic），只发送**外部输入（Input/Operations）**，让 Backup 自己执行一遍以达到相同状态。
- **基于的事实**：
  - 大多数软件在没有外部干扰时，内部执行是确定的（相同的初始状态 + 相同的指令序列 = 相同的结束状态）。
  - 不确定性主要来自**外部事件**（如网络包到达、键盘输入、中断）。
- **工作机制**：
  1. Primary 和 Backup 从完全相同的初始状态开始。
  2. Primary 接收外部输入（如客户端请求、网络包）。
  3. Primary 将这些**输入事件**按顺序发送给 Backup。
  4. Backup 按相同顺序执行这些输入。
  5. 两者状态保持一致。
- **优点**：
  - **网络开销小**：操作（Operation）通常很小（如 "读 Key 27"），远小于状态本身。这是人们偏爱它的主要原因。
- **缺点**：
  - **实现复杂**：必须严格保证 Primary 和 Backup 的执行顺序完全一致。
  - **处理非确定性指令困难**：如获取时间、生成随机数、获取 CPU ID 等指令，如果分别执行结果会不同。

#### 2. 复制状态机的技术挑战 (Q&A)

- **如果不一致会怎样？（脑裂风险）**
  - 如果 Backup 与 Primary 状态不一致（例如 Primary 认为分发了租约，Backup 不知道），一旦 Primary 故障，Backup 接管后会产生错误决策（重复分发租约）。这会导致系统逻辑崩溃，后果不堪设想。
- **如何处理非确定性指令（随机数/时间）？**
  - **策略**：Primary 执行这些指令，将**结果**作为数据流发送给 Backup。
  - **Backup 行为**：Backup 不真正执行该指令，而是等待 Primary 告知结果，并直接使用该结果。这样保证了两端看到的“随机数”是一样的。
- **多核/并行计算难题**：
  - VMware FT 的初代论文仅支持**单核 CPU**。
  - 在多核环境下，指令交错执行的顺序是不确定的（Non-deterministic），即使输入相同，最终状态也可能不同。这是复制状态机在多核时代面临的最大挑战。

#### 3. 复制级别：机器级 vs. 应用级

##### A. 机器级复制 (Machine Level Replication) —— VMware FT 的选择

- **复制对象**：硬件层面的状态（所有内存 bit、所有 CPU 寄存器）。
- **特点**：
  - **透明性（魔法棒）**：不关心跑的是什么软件（Windows, Linux, 数据库均可），只要能在支持的 CPU 上跑就行。
  - **无需源码**：不需要修改或理解应用程序代码。
- **代价**：需要处理极其底层的细节（如中断发生的精确指令位置），实现难度极高，效率相对较低。

##### B. 应用级复制 (Application Level Replication) —— GFS 的选择

- **复制对象**：应用程序逻辑层面的数据（如 GFS 的 Chunk, 数据库的 Record）。
- **特点**：
  - **高效**：只复制有意义的数据，忽略临时变量、UI 状态等无关信息。
  - **主流选择**：GFS、MapReduce 以及本课程大部分系统都采用此方式。
- **代价**：必须深入应用程序内部开发，容错逻辑与业务逻辑耦合。

#### 4. 实际运行中的关键问题

- **同步频率**：Primary 总是领先于 Backup。同步越频繁，Backup 落后越少，但性能损耗越大；同步越少，故障恢复时丢数据的风险越高。
- **故障切换 (Failover)**：
  - 当 Primary 挂掉，Backup 接管成为新 Primary。
  - **难点**：客户端如何感知？如何保证切换过程中没有请求丢失或异常？理想的“无感切换”在现实中极难做到。
- **添加新副本 (Re-replication)**：
  - 当一个副本挂掉，必须尽快补充新副本。
  - **必须使用状态转移**：因为新副本是从零开始，无法通过重放所有历史操作来追平（太慢），只能先拷贝一份完整的当前状态（State Transfer），然后再跟进最新的操作日志。

------

**总结**： 本节课通过对比，确立了 **复制状态机** 因其网络高效性成为主流选择的地位。同时指出，虽然 **应用级复制**（如 GFS）更高效且普遍，但 **VMware FT** 通过**机器级复制**提供了一种通用的、对业务透明的容错“魔法”，尽管它在处理非确定性指令和多核扩展上面临巨大挑战。

## 4.3  VMware FT 工作原理详解

#### 1. 基础架构：物理机与虚拟机

VMware FT 的核心思想是在两台不同的**物理服务器**上，分别运行**Primary VM（主虚拟机）\**和\**Backup VM（备份虚拟机）**。

- **物理层**：你需要至少两台物理服务器，因为容错的目标是抵御单台物理机的硬件故障。
- **虚拟化层 (VMM/Hypervisor)**：每台物理机上运行着 VMware 的虚拟机监控器（VMM）。VMM 负责模拟硬件，让多个操作系统在同一硬件上运行。
- **虚拟机层**：
  - **Primary VM**：运行在服务器 A 上，承载实际服务（如数据库、MapReduce Master）。
  - **Backup VM**：运行在服务器 B 上，作为 Primary 的镜像，处于热备状态。
- **网络环境**：两台服务器通过局域网连接，同时连接着客户端（Clients）和共享存储（Disk Server）。需要注意的是，VMware FT 通常使用**共享存储（Shared Disk）**，即 Primary 和 Backup 读写的是同一个远程磁盘阵列。

#### 2. 核心工作流程：确定性重放 (Deterministic Replay)

VMware FT 利用**复制状态机**原理，让 Backup VM 执行与 Primary VM 完全相同的指令序列。

##### A. 输入处理 (Input Handling)

当客户端向服务发送请求（网络数据包）时：

1. **数据包到达 Primary**：网络数据包到达服务器 A，触发物理中断。
2. **VMM 介入**：服务器 A 的 VMM 捕获该中断。它做两件事：
   - **本地投递**：在 Primary VM 中模拟一个虚拟中断，将数据包送给 Primary 的操作系统。
   - **转发给 Backup**：将该网络数据包的内容以及**关键的元数据**（如中断发生的精确指令位置）封装成 Log Entry，通过 **Log Channel** 发送给服务器 B 的 VMM。
3. **Backup 接收**：服务器 B 的 VMM 收到 Log Entry。它在 Backup VM 中模拟同样的虚拟中断，将同样的数据包送给 Backup 的操作系统。

##### B. 输出处理 (Output Handling)

Primary 和 Backup 都在运行相同的服务代码，处理相同的请求，因此它们都会生成回复报文。

1. **Primary 输出**：Primary VM 生成回复报文，通过 VMM 发送给真实客户端。
2. **Backup 输出**：Backup VM 也会生成完全一样的回复报文。但是，Backup 的 VMM 会**拦截并丢弃**这个报文。
   - **原因**：防止客户端收到双重回复，保持对外表现为一个单一的服务器。

#### 3. 特殊指令与非确定性 (The Log Channel)

为了保证 Backup 与 Primary 状态完全一致，VMM 必须处理所有**非确定性（Non-deterministic）**事件。

- **Log Channel**：这是 Primary VMM 向 Backup VMM 传输同步信息的专用通道。
- **同步内容**：
  - **外部输入**：如网络数据包。
  - **定时器中断**：Primary 的时钟中断会生成 Log Entry 发给 Backup，确保两者时间流逝感一致。
  - **特殊指令**：如随机数生成器、获取时间戳（RDTSC）等。
- **处理机制**：
  - Primary 执行这些指令（如生成随机数 `x`）。
  - Backup VMM 会**拦截** Backup VM 尝试执行该指令的操作。
  - Backup VMM 等待 Log Channel 传来 Primary 的结果 `x`。
  - Backup VMM 直接将结果 `x` 填入 Backup VM 的寄存器，**跳过**实际执行。这保证了两者得到完全相同的“随机数”。

#### 4. 故障检测与切换 (Failover)

系统必须能自动处理 Primary 或 Backup 的宕机。

- **故障检测**：

  - VMM 之间维持心跳（Heartbeat）。
  - Backup VMM 监控 Log Channel 的流量。由于 Primary 会频繁发送定时器中断 Log（每秒约 100 次），如果 Backup 超过一秒钟没收到任何 Log，它就会推断 Primary 挂了。

- **Backup 上位 (Go Live)**：

  1. **停止等待**：Backup VMM 不再等待 Log Channel 的事件，让 Backup VM 自由全速运行。
  2. **接管网络**：Backup VMM 会向网络发送广播（如 Gratuitous ARP），宣称自己拥有 Primary 的 IP/MAC 地址。网络交换机更新转发表，后续客户端请求将直接发给 Backup。
  3. **启用输出**：Backup VMM 不再丢弃输出报文，开始直接向客户端回复。

  - 此时，Backup 晋升为新的 Primary，服务恢复单点运行状态。

- **Primary 存活 Backup 挂了**：

  - Primary VMM 检测到 Backup 失联，会停止向 Log Channel 发送数据，作为单机继续运行。

#### 5. 总结

VMware FT 通过在 VMM 层捕获所有**输入**和**非确定性事件**，并将它们通过网络（Log Channel）精确地复制给 Backup，实现了对操作系统和应用程序透明的容错。Backup 虽然在“空转”（执行指令但不输出），但它时刻准备着在 Primary 倒下的瞬间无缝接管。



##  4.4 非确定性事件 (Non-Deterministic Events) 处理机制

目前为止，我们的讨论基于一个理想假设：只要 Backup 虚拟机接收到与 Primary 虚拟机相同的客户端请求，并执行相同的程序，它们的状态就会完全一致。然而，现实并非如此简单。

尽管大多数计算机指令是确定的（即结果完全取决于当前的内存和寄存器状态），但仍存在一类 **非确定性事件 (Non-Deterministic Events)**。如果不对这些事件进行特殊处理，Primary 和 Backup 的执行路径和最终状态将产生分歧。设计者的核心挑战在于如何捕捉并在副本间精确同步这些非确定性事件。

#### 1. 非确定性事件的分类

非确定性事件主要可以分为以下几类：

**A. 外部输入 (External Input)**

- **不可预测性**：客户端请求随时可能到达，其内容和到达时间不取决于服务器当前的状态。在网络系统中，这体现为网络数据包的接收。
- **中断处理 (Interrupts)**：数据包到达通常涉及两个步骤：
  1. 网卡通过 DMA (Direct Memory Access) 将数据拷贝到内存。
  2. 触发中断通知 CPU。
- **同步挑战**：对于操作系统而言，中断发生在指令流的哪个确切位置至关重要。如果 Primary 在第 N 条指令处处理中断，而 Backup 在第 N+1 条指令处处理，两者的执行路径就会分叉。因此，不仅数据包内容需要同步，**中断发生的精确指令位置**也必须同步。

**B. 怪异指令 (Weird Instructions)** 某些指令在不同机器或不同时间执行会产生不同结果，例如：

- **随机数生成指令**：硬件生成的随机数。
- **时间获取指令**：如 `RDTSC` (Read Time-Stamp Counter)，在不同时刻读取会得到不同数值。
- **系统信息指令**：如获取 CPU 唯一 ID (CPUID)。

**C. 多核并发 (Multicore Concurrency) —— VMware FT 未涉及**

- **竞态条件**：在多核系统中，不同核心上的指令交织顺序是不可预测的。例如，两个核心竞争同一把锁，Primary 上核心 1 抢到了，Backup 上核心 2 抢到了，后续状态将完全不同。
- **限制**：VMware FT 的初代设计仅支持 **单核虚拟机**。VMM 向 Guest OS 暴露的是单核 CPU，从而彻底避开了多核并发带来的非确定性难题。

#### 2. Log Channel 与同步协议

所有非确定性事件都必须通过 Log Channel 从 Primary 同步到 Backup。虽然论文未详述 Log Entry 的具体格式，但推测包含以下三个核心要素：

1. **指令序号 (Instruction Number)**：
   - 表示事件发生时，CPU 正在执行第几条指令（相对于机器启动以来的计数）。
   - 这是为了确保 Backup 能在完全相同的位置重放事件。
2. **日志类型 (Type)**：
   - 标识是网络数据包输入、怪异指令结果，还是定时器中断等。
3. **数据 (Data)**：
   - 对于网络包，即包的内容。
   - 对于怪异指令，即 Primary 执行该指令后得到的返回值。

**Backup 的行为**：Backup 虚拟机在执行到对应的指令序号时，会暂停执行，读取 Log Entry，利用其中的数据“伪造”执行结果（例如直接填入 Primary 生成的随机数），从而保持状态一致。

#### 3. 典型场景分析

**场景一：定时器中断 (Timer Interrupts)**

- **Primary 端**：物理服务器产生定时器中断，VMM 捕获中断，暂停 Primary VM，记录当前指令序号，将中断注入 Primary VM，并生成一条 Log Entry 发送给 Backup。
- **Backup 端**：Backup VMM 忽略自身的物理定时器中断。当收到 Log Entry 后，利用 CPU 的特殊特性（如性能计数器中断），让 Backup VM 精确执行到指定的指令序号后暂停，然后注入伪造的定时器中断。

**场景二：网络数据包与 Bounce Buffer**

- **DMA 竞争问题**：如果允许网卡直接 DMA 到虚拟机内存，VMM 将无法确定数据何时写入，也无法控制时序。
- **Bounce Buffer 机制**：
  1. 网卡先将数据包 DMA 到 VMM 的私有内存（Bounce Buffer）。
  2. VMM 捕获网卡中断，暂停 Primary VM。
  3. VMM 将数据从 Bounce Buffer 拷贝到 Primary VM 的内存。
  4. VMM 模拟虚拟中断通知 Primary VM，并记录指令序号。
  5. VMM 将数据和指令序号同步给 Backup，Backup VMM 执行相同的拷贝和中断注入操作。

#### 4. 关键 Q&A 解析

**Q: 这一机制依赖特殊的 CPU 硬件支持吗？**

- **A: 是的。** VMM 依赖 CPU 的性能计数器（Performance Counters）功能。VMM 可以配置 CPU 在执行了特定数量的指令后触发一个中断。这使得 Backup VMM 能够精确控制 Backup VM 在执行到与 Primary 相同的指令序号时暂停，以便注入事件。这是现代 Intel/AMD CPU 的标准功能。

**Q: 如果 Backup 跑得比 Primary 快怎么办？**

- **A: 绝对不允许。** 如果 Backup 执行超前，它可能在还没收到 Primary 的中断通知时，就已经执行过了该中断应该发生的指令位置。
- **同步机制**：Backup VMM 会监控 Log Buffer。
  - 如果 Buffer 为空，Backup VM 必须暂停等待。
  - 如果 Buffer 非空，Backup VM 被允许执行，但**最多**只能执行到下一条 Log Entry 指定的指令序号处。
  - 因此，Backup 总是至少落后 Primary 一条日志的延迟。

**Q: 怪异指令在日志中占比大吗？**

- **A: 非常小。** 绝大多数指令（如 `ADD`, `MOV`）是确定的。怪异指令（如获取时间、随机数）非常少见。Log Channel 的流量主要由网络数据包（I/O 输入）构成。

------

**总结**：VMware FT 通过强制 Backup 虚拟机在**相同的指令位置**处理**相同的数据**，解决了非确定性问题。它利用 Log Channel 传输外部输入和怪异指令结果，并依赖 CPU 的指令计数特性实现精确的执行流控制。



## 4.5 输出控制 (The Output Rule)

在 VMware FT 系统中，虽然 Primary 和 Backup 都在执行相同的指令并产生相同的输出，但通常只有 Primary 被允许向网络发送数据包，Backup 的输出会被其 VMM 拦截并丢弃。

然而，仅仅“丢弃 Backup 输出”是不够的。我们必须引入一条严格的协议——**输出控制 (Output Rule)**，以防止在故障切换时发生数据不一致。

#### 1. 问题场景：故障导致的状态回滚

为了理解为什么需要 Output Rule，让我们看一个没有它时会发生的灾难性场景。

**场景假设**：我们运行一个简单的计数器服务（当前值为 10），客户端发送一个“自增”请求。

1. **Primary 处理**：Primary 收到请求，将计数器从 10 变为 11。
2. **生成回复**：Primary 生成“当前值为 11”的数据包，并将其**发送给客户端**。
3. **发生故障**：就在发送完回复的瞬间，Primary 崩溃了。
4. **Log 丢失**：更糟糕的是，包含这个自增请求的 Log 条目在发送给 Backup 的途中丢失了（此时 Backup 的状态仍为 10）。
5. **Backup 接管**：Backup 检测到 Primary 宕机，上线接管服务。
6. **客户端重试**：客户端收到 TCP 连接中断或其他错误（或者客户端应用层重试），再次发送“自增”请求。
7. **数据不一致**：
   - Backup（新 Primary）收到请求，将计数器从 10 变为 11。
   - Backup 返回“当前值为 11”。

**结果**：客户端发起了两次自增，第一次收到了 11，第二次还是收到 11。这对于一个计数器服务来说是逻辑错误的（预期应该是 12）。 **核心矛盾**：客户端“看到”了 Primary 的执行结果，但 Backup “没看到”。当 Backup 接管时，系统状态实际上发生了**回滚**。

#### 2. 解决方案：输出控制协议

为了解决上述问题，VMware FT 制定了 Output Rule。 **核心原则**：**Primary 虚拟机只有在 Backup 虚拟机确认收到对应的 Log 条目后，才被允许将输出发送到网络上。**

**详细流程**：

1. **输入到达**：Primary VMM 收到客户端请求。
2. **发送 Log**：Primary VMM 立刻将该请求作为 Log 条目发送给 Backup VMM。
3. **执行与缓存**：
   - Primary VM 执行请求，生成输出包。
   - **关键点**：Primary VMM **拦截并缓存**这个输出包，**暂时不发送**给客户端。
4. **Backup 确认**：
   - Backup VMM 收到 Log 条目。
   - Backup VMM 发送 **ACK** 给 Primary VMM（注意：Backup 不需要执行完，只要收到 Log 就可以发 ACK）。
5. **释放输出**：Primary VMM 收到 ACK 后，才将之前缓存的输出包真正发送到网络上。

#### 3. 故障分析：Output Rule 如何生效？

如果在上述流程中发生故障（Log 丢失且 Primary 崩溃）：

- 因为 Log 丢失，Backup 永远不会发送 ACK。
- 因为没收到 ACK，Primary VMM 永远不会将“结果为 11”的包发给客户端。
- **结果**：Primary 崩溃，客户端什么也没收到（而不是收到 11）。
- **重试**：Backup 接管（状态为 10），客户端超时重试。Backup 处理请求，变更为 11，返回 11。
- **一致性**：对于客户端来说，这就像请求处理慢了一点，第一次失败了，第二次成功了。系统行为是线性的，没有发生逻辑错误。

#### 4. 性能权衡 (Performance Trade-off)

Output Rule 是所有强一致性复制系统的性能痛点。

- **延迟增加 (Latency)**：
  - 每一次输出（Output）都必须等待一次网络往返（RTT），即等待 Backup 的 ACK。
  - **同机房**：RTT 约为 0.5ms。
  - **跨城市（容灾）**：RTT 可能高达 5ms - 10ms。这意味着每个请求的响应时间至少增加了这么多。
- **吞吐量 (Throughput)**：
  - 虽然单次请求延迟增加了，但通过**高并发**处理，系统仍然可以维持较高的吞吐量（VMM 只是暂存输出，并不暂停 Primary VM 的 CPU 执行）。

这也是为什么类似 Google GFS 或 ZooKeeper 这样的系统倾向于使用**应用层复制**（Application-Level Replication）而不是机器级复制：

- 应用层复制可以理解操作语义，只对“写操作”做同步，对“读操作”可以直接返回。
- 而 VMware FT 这种机器级复制无法区分读写，必须对所有输出应用 Output Rule。

#### 5. 课堂 Q&A 精选

- **Q: VMM 具体是如何拦截输出的？**
  - **A:** 这是一个非常底层的实现细节。涉及到修改网络驱动、拦截 I/O 指令、内存页表控制等。通常由 C/C++ 编写，深入 Guest OS 的内核交互。
- **Q: 只有输出被阻塞吗？Primary 的执行会暂停吗？**
  - **A:** 是的，只有**网络输出**被 VMM 暂存了。Primary VM 的 CPU 可以继续执行后续指令，处理其他请求。这缓解了吞吐量问题，但改变不了单个请求延迟变高的事实。
- **Q: 能不能把 Log 存在 Primary 本地的物理内存里，不发给 Backup 以节省时间？**
  - **A:** **不行。** 容错系统必须假设“单机完全损毁”（包括内存数据丢失）。如果 Primary 掉电，本地内存里的 Log 就没了，Backup 接管后依然是旧状态，无法恢复数据。
- **Q: 有没有可能让 Backup 来发送输出？**
  - **A:** 这是一个非常聪明且有趣的思路！虽然 VMware FT 没有采用，但在某些最新的分布式协议研究中，确实存在类似的优化变种。



## 4.6 重复输出 (Duplicated Output) 与 TCP 去重

尽管我们使用了输出控制 (Output Rule) 来防止 Backup 在不知情的情况下输出数据，但在故障切换的临界点，仍然可能出现客户端收到**双份回复**的情况。

#### 1. 异常场景：双重回复是如何产生的？

让我们复盘一个典型的故障场景：

1. **正常回复**：Primary 虚机处理完客户端请求，生成回复报文。Primary VMM 收到 Backup 的 ACK（确认已收到请求 Log），于是将回复报文**成功发往客户端**。
2. **Primary 崩溃**：回复刚刚发出，Primary 就挂了。
3. **Backup 状态**：此时，Backup VMM 的 Log Buffer 里还堆积着那个客户端请求的 Log，Backup 虚机还没来得及执行到那一步。
4. **Backup 上线 (Go Live)**：
   - Backup VMM 发现 Primary 挂了，命令 Backup 虚机上线。
   - **追赶状态**：Backup 虚机首先必须消费掉 Buffer 里残留的 Log。这意味着它会**再次执行**那个客户端请求。
   - **生成输出**：执行完毕后，Backup 虚机也会生成一个回复报文。
   - **发送输出**：因为 Backup 已经上线（不再是 Backup），VMM 不再丢弃它的输出，而是直接发往网络。
5. **结果**：客户端先收到了 Primary 的回复，紧接着又收到了 Backup 的回复。**重复输出发生了。**

#### 2. 解决方案：TCP 协议的天然容错

这是一个明显的系统异常，但在 VMware FT 中，这个问题被**网络栈 (Networking Stack)** 自动解决了，无需在应用层做额外处理。

- **TCP 序列号 (Sequence Number)**：
  - 客户端与服务器之间通过 TCP 连接通信。
  - 由于 Backup 是 Primary 的精确副本，它们维护的 TCP 状态机完全一致。
  - Primary 生成的回复报文携带了特定的 TCP 序列号（例如 Seq=100）。
  - Backup 执行相同操作后，生成的回复报文携带**完全相同**的 TCP 序列号（也是 Seq=100）。
- **客户端去重**：
  - 客户端收到第一个报文（Seq=100），TCP 栈将其向上层应用提交。
  - 客户端收到第二个报文（Seq=100），TCP 栈检测到这是一个**重复序列号**的报文。
  - **动作**：客户端 TCP 栈直接**丢弃**第二个报文，仅仅回复一个 ACK（或者忽略）。
  - **应用层感知**：上层应用程序（如浏览器、数据库客户端）完全感觉不到收到了两份数据。

**结论**：对于基于 TCP 的服务，VMware FT 的重复输出问题被 TCP 协议本身的可靠性机制完美化解。如果应用使用 UDP，则必须在应用层实现去重逻辑（例如请求 ID）。

#### 3. 故障切换中的网络细节 (Networking Details)

在故障切换（Failover）过程中，网络层发生了一系列微妙的变化：

- **IP 与 MAC 地址**：
  - Primary 和 Backup 虚机拥有**完全相同**的 IP 地址和 MAC 地址。
  - 物理服务器（Host）只是载体，对网络透明。
- **交换机路径切换**：
  - **切换前**：交换机认为该 MAC 地址在端口 A（连接 Primary 物理机）。
  - **切换后**：Backup 上线，VMM 会发送一个 **GARP (Gratuitous ARP)** 广播。
  - **效果**：交换机收到广播，更新 MAC 地址表，将该 MAC 地址指向端口 B（连接 Backup 物理机）。后续流量自动流向 Backup。

#### 4. 关键 Q&A 解析

- **Q: 如果 Primary 发完回复就关闭了 TCP 连接，Backup 还能正常工作吗？**
  - **A:** 可以。Backup 会重放关闭连接的操作。
    - 如果客户端 TCP 连接已关闭，收到 Backup 发来的重复 FIN/RST 包，客户端会回复 RST 或忽略。
    - Backup 收到 RST 后，因为已经是单点运行（没有副本需要同步），它可以安全地处理这个错误并继续运行，不会导致状态分歧。
- **Q: Backup 发出的报文，源端口 (Source Port) 会变吗？**
  - **A: 不会。** Backup 的内存是 Primary 的逐位拷贝（Bit-for-bit copy）。TCP 控制块（TCB）里的源端口、序列号、窗口大小等所有状态都一模一样。所以 Backup 发出的报文在网络抓包看来，和 Primary 发出的没有任何区别。
- **Q: 这是否意味着我们需要依赖 TCP？**
  - **A:** 是的，或者依赖应用层去重。任何主从复制系统（Replication System）在切换瞬间都很难避免重复输出。如果不用 TCP，你就必须在应用协议里设计去重机制（例如给每个请求分配唯一 ID，服务端记录已处理的 ID）。在 Lab 2/3 中，你们将在应用层实现这种去重。

------

**总结**：VMware FT 允许在故障切换瞬间产生重复的网络输出。它依赖 **TCP 协议的序列号机制** 在客户端侧自动滤除重复报文，从而保证了应用层语义的正确性。这体现了系统设计中的一种权衡：允许底层的冗余，换取上层的简单性。





## 4.7 Test-and-Set 服务 ：解决脑裂问题

在此之前，我们一直假设故障模型是简单的 **Fail-stop**（即机器彻底宕机）。但在现实世界中，更危险的情况是**网络分区 (Network Partition)**。

#### 1. 问题：脑裂 (Split-Brain)

**场景**：

- Primary 和 Backup 所在的物理机实际上**都还活着**。
- 但是，它们之间的网络连接断开了。
- **后果**：Backup 收不到 Primary 的心跳，认为 Primary 挂了，于是试图上线接管服务。同时，Primary 依然在线。这会导致系统中有两个 Primary 同时接收客户端请求，产生数据分歧和破坏。这就是所谓的 **脑裂**。

在分布式系统中，**一台机器永远无法区分“对方挂了”还是“网络断了”**。因此，我们需要引入第三个独立的仲裁者。

#### 2. 解决方案：Test-and-Set 锁服务

VMware FT 引入了一个运行在外部（不与 Primary/Backup 同机）的 **Test-and-Set 服务** 来作为仲裁官。

- **机制**：
  - 这是一个存储在共享存储（或独立服务器）上的简单服务，维护一个标志位（Flag）。
  - 提供原子的 `Test-and-Set` 操作：读取旧值，写入新值（通常设为 1），并返回旧值。
- **仲裁流程**：
  1. 当 Primary 或 Backup 想要上线（Go Live）时，必须先向 Test-and-Set 服务发送请求。
  2. **原子操作**：服务执行 `read_and_set`。
  3. **胜者（Winner）**：第一个到达的请求会读取到 `0`（旧值），并将其置为 `1`。拿到 `0` 的副本获得“锁”，允许上线成为 Primary。
  4. **败者（Loser）**：第二个到达的请求会读取到 `1`（因为已经被前者改了）。拿到 `1` 的副本意识到有人捷足先登，因此**禁止上线**，从而避免了脑裂。

#### 3. 关键原则与 Q&A

- **Q: 只有在确认网络故障时才用这个服务吗？**
  - **A: 不，每次主从切换都必须用。**
  - **核心规则**：在分布式系统中，你永远无法确信对方是否真的宕机了。你只知道“我收不到他的消息”。因为无法区分宕机和网络分区，所以**任何时候** Backup 想要接管服务，都必须先去获取 Test-and-Set 锁。如果拿不到锁，就绝对不能上线。
- **Q: Test-and-Set 服务本身是不是单点故障 (SPOF)？**
  - **A: 表面上看是，但实际上不是。**
  - 如果 Test-and-Set 服务挂了，确实整个容错机制就失效了（没法进行故障切换）。这看起来有点讽刺：我们为了容错构建了复杂的 VMware FT，结果依赖于一个外部服务。
  - **实际情况**：VMware 使用的这个 Test-and-Set 服务通常运行在高可用的存储阵列上。这个存储系统内部本身也使用了**复制（Replication）\**和\**共识算法**（如 Paxos/Raft）来保证它自己的容错性。
  - **课程联系**：我们在 Lab 2 和 Lab 3 中即将构建的（Raft），正是用来实现这种高可靠、强一致的 Test-and-Set 服务的核心技术。

------

**总结**： 为了防止双主（脑裂），VMware FT 必须依赖一个外部的权威仲裁者。Test-and-Set 服务通过原子锁机制，确保在任何网络分区的情况下，系统中同一时刻**最多只有一个** Primary 能够上线。
